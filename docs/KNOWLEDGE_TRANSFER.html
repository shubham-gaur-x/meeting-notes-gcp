01What it is

A meeting-memory pipeline. It reads a Google Workspace account, extracts structure with an LLM, and stores it as a graph rather than as documents.

The point of the graph is that it answers questions a folder of notes cannot: who is central to this workstream, what did we decide about the SOW, what am I on the hook for. Meetings, people, topics, decisions and commitments are nodes; who attended what and what produced what are edges.

This is v6, a deliberate rebuild of a working local system (v5). Two things changed fundamentally, and they are the reason the port exists:

  • Airbyte is gone. Ingestion is four connectors we own, running as Cloud Run Jobs. v5 depended on a hosted product for this.
  • No in-process scheduler. v5 ran APScheduler inside its own web service. v6 uses Cloud Scheduler triggering stateless jobs, so nothing depends on a long-lived process staying alive.

Everything else — Memgraph, the extraction prompts, the Cypher, the test suite — was carried across on purpose rather than rewritten.

Read this first CLAUDE.md at the repo root is the authoritative spec — module boundaries, graph schema, conventions. docs/DECISIONS.md holds 24 ADRs explaining why things are the way they are. When this document and those disagree, they win.

02How data moves

Six stages, each a separate process. Numbered because the order is real — each stage only sees what the previous one committed.

1

Ingest

Four connectors fetch from source APIs and write raw payloads to one staging table. Each tracks a watermark so re-running is cheap and safe.

sources/gmail.py · sources/calendar.py · sources/meet.py · sources/jira.py · sources/runner.py
↓ staged rows, unprocessed
2

Claim

The drain claims a batch with SELECT … FOR UPDATE SKIP LOCKED, so two workers never take the same row. Exactly-once without a queue.

db.py · pipeline_drain.py
↓ one record at a time
3

Classify and route

A rules-based score decides whether a record is even a meeting — no LLM, no cost. Most email is not. Survivors get an extraction prompt chosen by meeting type.

classifier.py · meeting_type_router.py · prompts.py
↓ text + a prompt
4

Extract

Vertex Gemini returns structured JSON: title, attendees, topics, decisions, action items, blockers. Validated into Pydantic models; a malformed reply is not retried, because temperature 0 would return the same thing.

llm_client.py · extractor.py · models.py
↓ an ExtractedMeeting
5

Resolve and write

Attendees resolve to canonical people; unresolvable ones queue for review rather than being invented. The whole meeting commits in one transaction — it lands complete or not at all.

person_resolver.py · graph_client.py · pipeline.py
↓ graph write, then side effects
6

Enrich and act

Facts, relationships, causality and embeddings are layered on. Action items above the confidence threshold become Jira tickets; below it they go to a review queue.

memory/*.py · jira_pusher.py · dedup.py

A separate nightly job runs graph-wide work that makes no sense per-record: PageRank, community detection, memory consolidation, decay, and re-resolving people who were unknown when their meeting was first processed.

04Graph schema

Node types and the edges between them. Every node carries a deterministic id derived with uuid5, so reprocessing merges rather than duplicates.

LayerNodesKey edges
CoreMeeting, Person, Organization, Topic, Decision, ActionItemATTENDED, DISCUSSED, PRODUCED, FOLLOWS_UP, ASSIGNED_TO, WORKS_AT
MemoryFact, Preference, Procedure, ProcedureStep, MemorySessionHAS_FACT, PREFERS, KNOWS, INTERESTED_IN, PRECEDED_BY, CAUSED_BY
GovernancePersonReview, BlockerNEEDS_REVIEW, RAISES_BLOCKER
ProvenanceTicket, PullRequest, AgentRunTICKETED_AS, IMPLEMENTS, PRODUCED, RESOLVED_BY

The one rule to explain out loud Person.tracked defaults to false, and every per-person analytic — PageRank, centrality, community membership, the graph view — filters on it. Aggregates are the default; naming an individual is opt-in, and only the roster file can grant it.

This is why the dashboard's "Most connected people" panel reads empty. That is the gate working, not a bug — the panel says so directly.

05The dev agent

The part most worth demoing. Engineering action items become Jira tickets; the agent picks them up and opens pull requests.

It runs as a Cloud Run Job on a schedule. Each cycle: find labelled tickets in the active sprint, claim one, clone the repository the ticket names, create a worktree, run a headless Gemini CLI session inside it, then judge what came out.

Two layers decide whether it ships

Seven deterministic gates, each a pure function over the diff: tests green, lint and types clean, diff within budget, no protected paths touched, no new dependencies, no secrets, module boundaries respected. A gate that cannot run counts as a failure, never a skip.

An independent LLM reviewer then reads the ticket, the diff and the gate evidence. Only high-severity findings block; anything less is surfaced for the human.

If either layer objects, the run ends at NEEDS_HUMAN — terminal, so the poller will not retry it — and the PR is deliberately left open, because the work is real and just needs a person.

It never merges The agent has no merge path at all. CLOSED is written only by the GitHub webhook when a human actually merges the PR. That is the checkpoint.

Proven end to end

Ticket MNV-108 was picked up, implemented, committed, pushed and opened as a pull request. All seven gates passed, the reviewer approved, the ticket moved to In Review, and provenance was written to the graph as AgentRun -[:PRODUCED]-> PullRequest.

06Rules that hold

These are enforced by tests and by a guardrail gate. Breaking one is usually the sign of a misunderstanding rather than a shortcut.

  • One module owns each external system. SQL only in db.py, generic Cypher only in graph_client.py, MAGE calls only in graph_algorithms.py, Jira REST only in jira_client.py.
  • Only config.py reads the environment. Everything else takes settings as an argument, which is why the suite runs with no .env.
  • One transaction per meeting. Never a sequence of driver calls that can half-succeed.
  • MERGE, never CREATE, for anything with a deterministic id.
  • Topic keys are lowercased and trimmed. Raw casing fragmented single topics across several nodes in v5 and quietly understated every insight.
  • No scheduler inside a process. Cloud Scheduler triggers stateless jobs.
  • Tests never need credentials. All 665 run offline against fixtures.

09Bugs worth knowing & resolutions

Each of these looked like working code and had passing tests. They show where failure was hidden and how each has been resolved.

Green tests, wrong data (Resolved) A unit test asserted that extract_overrides() returned the right dict, and it did. The bug was one layer up: model_copy(update=…) does not validate, so the overridden attendees stayed raw dicts, and getattr on a dict silently returned defaults. Resolved by enforcing ExtractedMeeting.model_validate().

  • Ground truth thrown away (Fixed). Calendar API returns exact invitee addresses. Adapter now passes full attendee rosters directly to the graph writer.
  • Producer and consumer disagreed (Fixed). Jira ticket labeling aligned with the dev agent's pollers.
  • A query that matched nothing (Fixed). Replaced rigid sprint JQL with active board state queries.
  • Counting distinct values, not items (Fixed). Fixed Cypher aggregation over distinct node entities.
  • Order-dependence on attendee resolution (Fixed). The nightly graph pass re-resolves and links unassigned actions.
  • Memgraph pattern sorting constraint (Fixed). Replaced pattern expressions in ORDER BY with OPTIONAL MATCH degree counts.
  • Action item status overwrite on re-ingestion (Fixed). Cypher MERGE now uses CASE WHEN coalesce(a.done, false) = true THEN true ELSE $done END.
  • FastAPI query ceiling 422 error (Fixed). Raised query ceiling limit to 5,000 for large-scale enterprise batches.

The pattern is consistent: none of these were caught by tests, and all were caught by running the system against real data and reading the output. That is worth carrying forward.
